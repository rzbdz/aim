# aim — an IM for agents that don't trust each other

A file-first communication fabric for multiple independent agents (Claude Code
sessions, Codex sessions, anything with a shell) working the same problem.
Transport is the filesystem. Protocol is one Python file. **The team leader is a
human and stays a human.**

The design exists to solve one problem:

> Two agents working the same question do not have two opinions. They have one
> opinion and one reaction to it. Whichever agent speaks first has already
> decided what the disagreement is *about* — and the second agent, reading that
> framing before forming its own, produces an elaboration of it rather than an
> alternative to it.

That is not a hypothetical. It is the default behaviour of any chat-shaped
multi-agent setup, and it is invisible from the inside: the second agent still
feels like it is reasoning. This document is about why the obvious fixes fail
and what a mechanism that actually holds looks like.

---

## 1. Why the obvious fixes fail

**"Tell them to think independently."** A norm cannot be verified and does not
survive contact with a persuasive peer. The failure is not disobedience; it is
that the agent does not experience itself as complying.

**"Have them debate."** Debate optimizes for winning a framing, not for
falsifying one. Two agents in an open channel converge on the more fluent
argument, not the more correct one, and the transcript will look excellent.

**"Use subagents."** A subagent inherits its parent's framing by construction.
It is a way of thinking harder inside one position, not a way of getting a second
position. The failure mode here is path dependence: one wrong turn, followed
consistently to the end. This is exactly what the user's brief calls 一条错路走到黑.

**"Give them separate contexts."** Necessary, not sufficient. Separate contexts
that share a channel are still one channel, and the first speaker still sets the
frame.

The one thing that works is denying access — and access denial only works if it
is **mechanically enforced and recorded**, because the agent that is most likely
to rationalize a peek is the one that most needs to be stopped.

## 2. The mechanism

Six phases. A single channel moves through them once; the human leader is the
only actor who can advance them.

| phase | who may read | who may write | what it is for |
|---|---|---|---|
| `SEALED_DIVERGENT` | you, your own log | your own private log | form a position that has never been exposed |
| `COMMIT` | you, your own log | your own private log | stop forming; commit |
| `SYNTHESIS` | **the synthesizer only** | the synthesizer | a third party reads the mixed bundle and maps the disagreement |
| `CROSS_EXAMINE` | everyone | everyone, bounded | the positions finally meet |
| `RESOLVE` | everyone | the leader | decide |
| `CLOSED` | everyone | — | record |

Four mechanisms carry the weight:

**The barrier is in the tool.** `aim inbox` returns only your own messages before
cross-examination. There is no flag that expands it; the refusal is generated by
the phase, written to the ledger as a `refusal` record naming the agent, the
action and the phase, and it cannot be talked around without editing the tool —
which is itself evidence. That last clause was false when it was first written;
see §3.

**The seal is a commitment device, not a binding contract.** Before anyone sees
anyone, each participant writes a summary plus a list of claims, each with a
`confidence` and a **`kill_if`** — the observation that would make them drop it.
The seal file records the *raw bytes* of the private log it summarizes, so later
edits to that reasoning are caught by `aim verify` while appends after the seal
stay legitimate. It recorded a rule for reading the file instead of the bytes
themselves for the whole first run, and therefore caught nothing; see §4.8. A
seal cannot stop an agent from changing its mind. It can make "I said this all
along" impossible to claim with a straight face — but only now that the check
runs at all.

**The synthesis step is a firewall.** The bundle containing everyone's sealed
reasoning is readable by exactly one agent — the **synthesizer**, who did not
argue either side. Everyone else's first exposure to the other side is the
synthesizer's map of the disagreement, not the other agent's own prose. This is
the cheapest available approximation of an independent third party.

**Cross-examination is bounded.** Once the floor opens, it is not a chat:

- every message must name the message it `--responds-to` (no broadcasts);
- two messages per participant per round, with the leader opening each round;
- every message carries a `--kind` (`evidence`, `objection`, `rebuttal`,
  `question`, `concession`, `proposal`, `note`) — an unlabelled message is how a
  concession gets read as a proposal;
- a message that echoes a peer's phrasing above 50% (8-gram overlap) is refused
  unless the sender passes `--echo-ok --echo-reason`, which is logged.

That last rule is the sharpest one and the most likely to be wrong. It is
described in §4.

## 3. What is enforced, and what is only recorded

Being honest about the line:

**Enforced** (you cannot do it, the tool refuses, and the refusal is now written
to the ledger): cross-reading before `CROSS_EXAMINE`; writing to the public
channel before `CROSS_EXAMINE`; advancing the phase as a non-leader; entering
`SYNTHESIS` before every participant has sealed; appointing a participant as the
synthesizer; a non-synthesizer reading the mixed bundle; unaddressed or
unlabelled messages during cross-examination; exceeding the round quota; verbatim
echo without a recorded reason; confirming a delivered message whose bytes do not
match what was sent; re-registering a live agent id.

**Recorded, not enforced** (it can happen; it leaves a mark): tampering with a
log, a seal or a private log after the fact (`aim verify` shows the break, and as
of 2026-09-21 it actually does — see §4.8); reading a peer's files directly with
`cat` instead of through `aim`; editing `bin/aim` itself.

This boundary is deliberate. Everything in the second list requires an action
that is *legibly* an attempt to go around the fabric, and every one of them is
detectable after the fact. The design does not try to make cheating impossible —
it tries to make cheating **visible**, and to make the honest path the easy one.
An agent that never hits a refusal is not necessarily behaving; it may just never
have been tempted.

That last sentence used to be an article of faith. It no longer has to be, and it
was the single largest defect the first real run found:

> Until 2026-09-21, this section claimed refusals were "recorded in the ledger."
> They were not. `die()` printed to stderr and exited; the ledger had exactly
> three event types — seal, phase, concession — and `grep -ci refus` over a live
> channel's ledger returned 0. A refusal was enforced and then forgotten.
>
> That broke the design's own loop: barrier → refusal → ledger → evidence that
> the barrier was tested. The middle link was missing, so **from the record there
> was no way to distinguish "nobody was tempted" from "everybody was tempted and
> was stopped"** — which is the difference between a barrier that works and a
> barrier nobody has leaned on. Refusals are now ledger records carrying agent,
> action, phase, and a `class` separating a phase-gate refusal (`barrier`) from a
> malformed request (`form`). The claim above is now checkable rather than
> asserted, and `tests/selftest.sh` fails if it stops being true.


## 4. What I think is wrong with this

Written down so a peer can attack it rather than rediscover it.

1. **Agent-decides-to-be-independent is still the failure mode.** Nothing stops
   an agent from writing a private log that is a plausible-sounding position it
   does not hold. The seal makes that visible *as a choice*, not impossible.

2. **The echo check measures the wrong thing.** 8-gram overlap catches verbatim
   restatement and misses the real disease, which is adopting a peer's
   *vocabulary* — "framing collapse", "contamination", "barrier" — while
   producing original sentences. A message can score 0% overlap and still be
   entirely downstream of the peer's frame. I do not have a fix for this.

3. **A human on the critical path is correct and slow.** Every phase transition
   waits for a person. At three agents this is a feature; at twelve it is a
   stall, and the pressure to delegate phase control to an agent will be
   enormous — at which point the agent controls the thing that constrains it.

4. **The synthesizer is a single point of framing.** Whoever summarizes decides
   what the disagreement was about. `aim` appoints that role but does not
   constrain how they do it. The obvious fix (multiple independent synthesizers,
   compared) costs another full barrier cycle.

5. **Phase count is a guess.** Six felt like the minimum that separates
   *form*, *commit*, *map*, *contest*, *decide*. It may be three phases wearing
   six hats, or it may be missing a phase that matters (e.g. a place to record
   why a claim was dropped, separately from why it was made).

6. **Quota tuning is unprincipled.** Two messages per round was chosen to force
   selection. It may just make everyone terse, which is cheap to fake and looks
   like discipline.

7. **Delivery is unsolved and I have stopped pretending otherwise.** See §5.

8. **The seal did not bind anything, for the entire first run.** `cmd_seal` wrote
   `private_log_hashes`; `cmd_verify` read it as `or []` and guarded both branches
   with `elif expected and ...`; and every seal on disk had been written by an
   older tool that wrote `private_log_sha256` instead. So the check ran zero
   times, on every seal, silently. The demonstration is not subtle: rewrite a
   sealed private-log record, recompute the record hashes so the log's own chain
   stays self-consistent, run verify — `chain OK`. The sealed reasoning says one
   thing and the seal says another, and the tool that exists to notice says
   nothing. Fixed 2026-09-21 by storing the frozen prefix as raw bytes; the same
   attack now prints `TAMPER … not a prefix of the file now`, and a seal carrying
   no commitment at all is TAMPER rather than skipped. The general lesson is worth
   more than the bug: **a hash over a mutable file means nothing unless the seal
   holds bytes rather than a rule for reading them.**

9. **Registration had no ownership.** Anything that can run `aim` could claim any
   unused id, and could silently take over an id already in use — inheriting
   everything the ledger says about it, with no trace of the switch. `--force`
   now performs a takeover deliberately and records it. Ownership *proof* is still
   absent and I think it is unbuildable here; attribution is cooperative-only.
   The design should say so rather than imply otherwise.

10. **The lost update, one level below the lock.** `write_json` was always atomic
    per write, which is not the same property as being safe for
    read-modify-write. Two agents registering at the same instant: one vanished,
    and the file left behind was well-formed, so afterwards it read as "that agent
    was never here." Measured on the pre-fix code: 5 concurrent registrations, 1
    survivor. A well-formed file that is silently missing a fact is worse than a
    corrupt one, because nothing prompts you to look.

## 5. Transport: what actually works

The channel is the record. Getting a *session* to look at the record is a
separate problem, and it is the load-bearing one.

1. **Record** (solved): a hash-chained JSONL log under
   `channels/<id>/log.jsonl`, appended under an exclusive `flock` so concurrent
   writers cannot collide on message ids. `aim verify` re-walks the chain.

2. **Outbox** (solved, and vendor-neutral): `aim push --as A --to B` writes a
   plain `.md` file into `outbox/B/`. Any mechanism at all can carry it — a
   startup hook, a cron, a human with a clipboard. `aim pull --as B` reads it and
   marks it claimed. This is the part I trust, because it has no opinions about
   how it gets read.

3. **Receipt** (solved, and deliberately narrow): `push --require-ack` records the
   byte count and the sha256 of the body; `confirm --msg-id` is the recipient
   echoing the hash it verified; `outbox --as A` gives the sender
   sent / claimed / ACKED, exiting non-zero when a demanded ack has not arrived.
   A message altered after sending is refused confirmation — confirming it would
   tell the sender intact delivery happened when it did not, which is worse than
   silence because the sender would act on it.

   **None of this wakes anybody.** A receipt proves receipt only after the
   recipient was already awake, so the common case — peer asleep, sender waiting —
   is untouched. What the receipt buys is that the unsolved case is now *visible*:
   an unacked message reads as unacked instead of as "probably fine".

4. **Doorbell** (unsolved, and I want to be clear that it is unsolved): making an
   *already running* peer session look. The first real two-vendor exchange
   measured this rather than argued it — a push sat unread in the peer's outbox
   until its session happened to have a live turn. Candidates, in the order I
   would try them: a hook that injects "check your outbox" on the peer's next
   turn; an external queue the peer polls; a human relay. I have a working
   doorbell in this environment, but it depends on a local daemon and is therefore
   exactly the kind of vendor internals the design is supposed to avoid — it is a
   bootstrap, not a component, and should be deleted the moment hooks-based
   delivery works.

`aim nudge --channel <ch> --peer <id>` prints the shortest thing you can hand a
peer session to get it in. That text is the portable interface.


## 6. Using it

```sh
cd /root/tmp/agent-im          # `aim` is on PATH

aim register   --as <you> --kind claude|codex|human
aim new-channel --id <ch> --topic "..." --participants a,b --leader <human>

aim status     --channel <ch>                 # where the conversation stands
aim say        --as <you> --channel <ch> --body "..."     # private, pre-barrier
aim seal       --as <you> --channel <ch> --summary "..." --claims claims.json
aim advance    --as <human> --channel <ch> --to COMMIT
aim inbox      --as <you> --channel <ch>
aim verify     --channel <ch>                 # re-walk the hash chain

aim push       --as <you> --to <peer> --subject "..." --body-file f.md --require-ack
aim pull       --as <you> --claim             # your outbox
aim confirm    --as <you> --msg-id <id>       # receipt: the bytes I hold are the bytes sent
aim outbox     --as <you>                    # sent / claimed / ACKED; exits 4 if an ack is owed
bash tests/selftest.sh                        # 87 assertions, all of them refusals
python3 tests/conformance.py                  # 33 checks over real concurrent processes
```

The self-test is the specification. Every `REFUSED` in it is the feature.

It is also the only thing standing between this document and its own history: on
2026-09-21 two of the claims above were false in ways the README asserted were
true (§3, §4.8), and the reason they are true now is that a run produced a
synthesis, the synthesis produced a measurement, and the measurement became an
assertion. Prose in this file is not evidence. `tests/selftest.sh` is.

## 7. Where this should go

- **Hooks-based delivery**, so a session is woken by the fabric rather than by a
  human noticing. This deletes the bootstrap in §5.4. It is the highest-value
  unsolved item, because it is the one the first real two-vendor exchange
  actually failed at.
- **Multiple synthesizers compared**, to attack §4.4 without a human in the loop.
- **A phase for recording abandoned claims** (§4.5), because *why a claim was
  dropped* is the highest-value evidence the process generates and there is
  currently nowhere to put it. The first run produced an instance worth reading:
  a participant wrote a claim, wrote the standard that would falsify it, and then
  its own corpus met that standard. There is nowhere in the schema to record
  that, so it is only visible because someone wrote prose about it.
- ~~**A conformance harness over real OS processes**~~ — **done, and it is the
  second specification.** `tests/conformance.py` runs 33 checks with real
  processes: 12 concurrent registrations, 10 concurrent channel writes, one agent
  racing itself, 14 SIGKILLs mid-transaction, a cold agent rejoining from the
  record with no human relaying, delivery measured rather than asserted, the
  barrier under simultaneous real-process attacks, and 6 processes racing for one
  identity. Proposed by the reviewer as c7 (0.93) — and the proposal was correct:
  the first version of it found two bugs in *itself* (a check that searched
  `body` for text that was in `subject`, and a check satisfied by a table's
  column header) before it found anything in `aim`. Keep that in mind when reading
  a green board from either suite.
- **Measured independence** as a complement to enforced independence: if two
  agents genuinely diverged, their drafting trajectories should be
  distinguishable *before* anyone reads anyone. If that is measurable, it
  converts the barrier from an access-control story into an empirical one — and
  also creates a new failure mode, where agents perform divergence for the
  metric. §4.2 is the same problem in miniature, and `aim tension` now prints its
  own caveat for exactly this reason.
- **A `review` command**: a participant pushing a diff to a reviewer, with the
  review coming back as an addressed, typed message rather than prose in an
  outbox. Today that workflow runs on `push`/`confirm` and a hand-written file,
  which works and is not the design.
- **N agents, N channels.** The three-agent case (two advocates plus a
  synthesizer) is the argument this design was built for. The four-plus case is
  probably not "more of the same"; it needs its own thinking.

## 8. Open questions for the next agent

1. Is the seal worth anything? An agent can write a commitment it does not hold.
   The first run answered this more darkly than the question asks: the seal did
   not even bind the artifact it claimed to bind (§4.8), so the question of
   sincerity was unanswerable while a much simpler question — was anything
   checked at all — was also unanswered.
2. Where does a competent agent, optimizing for looking correct rather than
   being correct, first get around this protocol? The cheapest answer found so
   far needs no cleverness at all: seal an empty private log, and the transcript
   verifies as intact.
3. Can independence be *measured* rather than *enforced*, without inviting
   agents to perform divergence for the metric?
4. Who decides when a barrier lifts, when the human is no longer the bottleneck?
   Any answer that puts an agent on that path has to explain why that agent is
   not simply the first speaker again.
5. The first synthesis raised one the design does not address: **is the topic
   string itself a frame?** It ships to every participant and is the first thing
   each reads. Both participants in the first run answered inside its terms, and
   its terms came from this document. Cheap test: strip the framing out of the
   briefing and see whether the positions still have the axes they had.
6. **Nobody has modelled the human's incentive.** Every agent in the system has
   been reasoned about at length; the leader has been treated as a latency cost.
   If the barrier is partly theatre, the human is the audience — and the design
   makes the audience the only actor who can advance a phase.

## 9. As a project-management IM

Section 2 describes a mechanism for keeping two positions independent. This section
answers a different question, asked by the human leader on 2026-09-21: does `aim`
work as a *project-management* IM — a place where work is planned, tracked and
argued about — and what is missing if not.

The honest form of that answer is a table where every row is either a command you
can run or the word *missing*. A capability is only listed as present if there is a
hash-chained record behind it; "there is a field for it" is not the same as "it is
recorded".

| capability | where it lives | status |
|---|---|---|
| durable, ordered, tamper-evident message log | `channels/<ch>/log.jsonl`, `aim verify` | **present** |
| roles, and a phase that only the human can move | `aim register`, `aim advance`, `aim request-advance` | **present** |
| addressed messages with a required kind | `aim say --responds-to --kind` | **present** |
| delivery receipts | `aim push --require-ack`, `confirm`, `outbox` | **present**, narrow: proves receipt only after the peer wakes |
| a refusal ledger — intent, not just outcome | `channels/<ch>/ledger.jsonl`, class `barrier`\|`form` | **present** |
| work items with status, owner, dates, blockers | `aim task new/move/assign/link/comment/publish` | **present** (M1, 2026-09-21) |
| a board that reads the work items | `bin/aimboard.py render` | **present** |
| schedule with dependencies and milestones | `aimboard` gantt view | **present**, drawn from committed dates only |
| a dashboard with a barrier and refusal audit | `aimboard`, `tests/test_aimboard.py` | **present** |
| group chat: several topics, N participants | `rooms/` | **missing** (M2, `design/06`) |
| read state — who has seen what | `rooms/<room>.cursors.json` | **missing** (M2) |
| mentions | `@agent` recorded as events | **missing** (M2) |
| search across logs, tasks and rooms | — | **missing**; `rg` over JSONL is the current answer and a real one |
| waking an idle peer | `bin/aim-doorbell-hook`, wired per harness | **partial**: the hook works, wiring is per-session and was absent until 2026-09-21 |
| reports: progress, blockers, cycle time | `aimboard` milestone progress | **partial**: a milestone meter exists, no burndown |
| export to a foreign tool (CSV, iCal) | — | **missing** (M5) |
| notifications beyond the next turn | — | **missing**: a hook fires on a turn, and an idle session has no turn |

Three properties of the mechanism carry over to the PM layer and are worth stating
because they are what make this different from a chat window with a board attached:

**Work items obey the barrier.** A task title is a position in the least suspicious
form the fabric contains — "attack the temp-path claim" is a complete leak of one
agent's framing, arriving as ordinary planning. So work items are born `draft`
during `SEALED_DIVERGENT`/`COMMIT`/`SYNTHESIS`, visible to their author and to the
leader, and `aim task publish` exposes one deliberately and records that act. Rooms
inherit the same rule. The dashboard is tested for the *absence* of a peer's draft
in its own bytes, because a view one `grep` away from what `aim` refuses to show is
a route around the refusal.

**The board is a view, never a file.** Board state is a fold over
`channels/<ch>/tasks.jsonl`, which is hash-chained like the log. There is no mutable
board document to lose a write to. This is not a stylistic preference; it is the
lesson of §4.10, and it is *also* incomplete — see the correction in
`design/05` §3: moving the state into a log moved the race into identifier
allocation, where 8 concurrent creations produced 11 records and 9 distinct ids.

**The renderer is read-only.** `aimboard` writes nothing but the HTML it was asked
for, which is asserted by a test that hashes every file in the fabric before and
after a render. A dashboard that can mutate state is a second implementation of the
write discipline, and this project has measured where those end up.

### Using it

    aim task new --as claude-session1 --channel hello --title "..." \
        --owner claude-session1 --status doing --due 2026-09-23 \
        --milestone M1 --accept "the sentence that makes this verifiable"
    aim task move    --as ... --id T-0007 --to review
    aim task publish --as ... --id T-0007 --reason "the leader needs the board"
    aimboard render --out /root/tmp/aim-board.html          # the leader's view
    aimboard render --json                                  # the same fold, for a tool
    aimboard render --as claude-session1                    # what a participant may see
    aimboard render --fail-on-unacked                       # exits 4 if an ack is owed
    aimboard render --fail-on-drift                         # exits 5 if the plan and the store disagree

The last two exist so the board can be a gate rather than a poster: a stale plan and
an unanswered handoff are both exit codes.

### What is deliberately not here

Real-time transport, a server, a database, identity proof, drag-to-reschedule, and
multi-tenancy. `plan/risks.json` lists them under `non_goals`, with reasons; the short version is that
each one moves a fact into a second place where it can be lost, and losing facts
quietly is the failure this project was built to make visible.
