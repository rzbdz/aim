## 2. Three implementations of one rule, three answers

| gate | withholds from this seat | file |
|---|---|---|
| `bin/aim _visible_to` — what `aim task list` serves | **26** | `bin/aim:1926` |
| `aimboard gate.visible_tasks` — what the board serves | **35** | `aimboard/gate.py:52` |
| `aimboard a2a.task_visible` — the union the module says is the one | **35** | `aimboard/a2a.py:761` |

Measured on the same 98-card store, same seat, same moment. The board hides 9
cards the CLI would serve: **T-0245 … T-0253**.

Six of the nine are T-0246..T-0253, and the cause is written down in the tree
already: `bin/aim`'s fold reads `created_by` off the `created` event
(`bin/aim:1866`), so `aim task list` serves a card to the seat that typed it even
when a peer owns it. `aimboard/fold.py` copies only `PLAN_FIELDS` off that event
and never sets `created_by` — so the gate's creator arm cannot fire, and the same
six cards vanish from the board. The store carries no `created_by` field at all
(0 of 99 `created` rows), so this is a derived field kept by one reader and
dropped by the other. `aimboard/a2a.py:639` documents exactly this, measured, and
names the consequence: *"the union's second arm has nothing to fire on."*

The other three — T-0245, T-0249, T-0250 — are unowned. `bin/aim:1929` states the
leader's rule: *"An unowned work item is readable by everyone in every phase …
it is an offer of work"*, and `_visible_to` returns True for them. The board
withholds all three.

Consequence for the goal: **the front end cannot reach zero unfinished while the
channel is in `COMMIT`**, because 27 of the 29 are drafts and the gate is an
absolute refusal, not a display filter. But it is also true that the front end is
hiding 8 unfinished cards it is entitled to show (10 by `bin/aim`'s rule, 2 by the board's), and none of this is the
`read_others` barrier you would be opening by advancing. `gate.visible_tasks` and
`a2a.task_visible` are codex's files (`aimboard/` is his lane, design/05 §8); I
have not touched either.

## 3. `reports.series` is broken in two separate ways

The done/undone curve you asked about is `reports.series`, 14 points, and it is
wrong twice:

```
2026-09-10 .. 2026-09-21   {remaining: 0, done: 0}     <- eleven days
2026-09-22                 {remaining: 32, done: 65}
2026-09-23                 {remaining: 33, done: 0}    <- today
```

* **The leading zeros are synthesized.** Those eleven days hold no data at all;
  they are `0`, not `null`, so an empty day and a day with nothing remaining draw
  the same point. The store's first row is 2026-09-21T07:33Z — the fabric is two
  days old, and the curve claims twelve.
* **The last point is a partial day.** `done: 0` on 2026-09-23 against `done: 65`
  on the day before, in a channel where nothing has moved since 2026-09-22
  because `COMMIT` refuses the move. So the "done" line takes a visible step
  *down* every morning and climbs back during the day. That is almost certainly
  the artifact you saw.

This one is a display bug with a real consequence: a curve that resets its last
point daily is a curve nobody can read, and it is describing a fabric whose whole
thesis is that a number measured at one state must not be quoted at another.
