## 1. An incident, first, because it is mine and it touched the live root

While measuring the human's verbs I built throwaway probe roots in `/tmp` and
**three of the four probes went to the live root instead.** Cause: `bin/aim:35` is

    ROOT = Path(os.environ.get("AIM_ROOT", "/root/tmp/agent-im"))

— the default is the *live* checkout, there is no `--root` flag, and I exported
`AIM_ROOT` in the same shell **one step too late**, after the writes. What landed
on the live tree:

| what | where | when |
|---|---|---|
| registry entries `a` and `b` (`--kind claude`) | `registry.json` | 17:58:23Z |
| channel `c`, with 3 refusal rows | `channels/c/` | 17:58:23Z |

No `task new`, no `advance`, no `seal`, no `register --force`. Nothing overwrote
an existing id. I removed both. `git checkout -- registry.json` (the diff was
exactly those two `id` blocks and nothing else) and `rm -rf channels/c`
(untracked, 0 tracked files, created 01:58 CST). Archived first, at
`/tmp/aim-tasks/pollution/`: the manifest, the three refusal rows, and
`registry.json.{before,after}`.

**Then I checked the time range that was actually at risk, because `aim verify`
was saying something alarming.** `aim verify --channel hello` returns
`chain BROKEN` — but it returns that on **HEAD's own committed ledger**, which
I proved by extracting `git archive HEAD channels/hello` into a temp root and
running the tool's own verify on it: same `TAMPER … carries no private-log
commitment` ×2, same `chain BROKEN`. So that brokenness is pre-existing and not
mine. The chain rows I walked by hand — every writer is append-with-`prev`, and
no row reads a sibling's `prev` — say the same thing.

**The exposure is smaller than the alarm.** Every row that was at risk is inside
`2026-09-22T17:58:23.600Z … .999Z` (the three probes are 250 ms apart). In that
window the only survivor on the live ledger is `channels/hello/ledger.jsonl`
row 322, `17:54:02.436Z`, a *read* (`task list`) — three minutes before, and no
row landed after it. So **no write of mine, and no concurrent write by anyone
else, was clobbered.**

I am reporting this rather than quietly fixing it because it is exactly the
shape this project keeps measuring, one level out: **a tool whose default action
is a write to the shared store, whose only way to say "not the shared store" is
an environment variable, and which gives no signal that it went to the default.**
`register` even prints `aim root: /root/tmp/agent-im` — the fact was on screen
and I read past it. Two candidate remedies, both codex's lane:
`aim` refuses to write when `AIM_ROOT` is unset, or `aim` prints the root on
*every* verb and not only on `init`. The second is the cheaper one and would have
caught me.

## 2. The curve: it exists on the server, the page draws a different one, and neither is a curve

You asked *"为什么 done、undone 没曲线"*. Measured on the live board right now
(`/api/state`, payload `2026-09-22T17:56:32Z`):

    reports.series = 14 buckets, 2026-09-09 … 2026-09-22
                     13 of them are {remaining: 0, done: 0}
                     bucket 14 (09-22) = {remaining: 25, done: 65}
    reports.with_history = 65   reports.recorded = 90   reports.seed_only = 87

So the chart is a flat line for thirteen days and **one vertical wall on the
last day** — which is what you are looking at. It is not a rendering bug.

**It is also not a data bug. There is no other fourteen days to draw.** The whole
record begins `2026-09-22T02:40:32.818Z` and ends `2026-09-22T15:12:08.088Z`:
**12.5 hours, all of it on one calendar day.** `report_data`'s window is
`days=14` (`aimboard/fold.py:298`), is never overridden anywhere — the one
production call site, `aimboard/api.py:414`, passes only `as_of` — and a fixed
day-width window over a one-day record can only produce one non-empty bucket.
Day resolution is structurally unable to show anything else.

**And the server already has the right series.** `GET /api/flow` exists, is
routed (`aimboard/cli.py:543`), is documented, and returns a bucketed
opened/done series with `totals`, `sources` and provenance. Measured:

    /api/flow?window=14d&bucket=1d  -> totals {opened: 70, done: 59}
    /api/flow?window=24h&bucket=1h  -> the same 129 events, at hourly resolution

Its own docstring says it was built for exactly this (*"a chart that counted a
peer's divergence-phase draft would be a route around a refusal `aim` records"*),
and **nothing reads it.** `grep -rn "api/flow" web/src web/tests` → **zero hits.**
The front end's complete endpoint list is `/api/state` (14 references),
`/api/revision`, `/api/digest` and `/api/command`. So there are two
implementations of one series — the server's `flow_series` and a second one
computed in the browser inside `ReportsPane.vue` — and the page draws neither:
the burndown card draws `board.report.series`, the day-bucketed one, and the
per-minute flow card re-derives its own from `task.events` client-side.

**The minimum fix is one line, and it is not a new feature:** either the
`/api/flow` route is what the burndown card reads, or `report_data`'s `days=14`
becomes something the caller supplies and `as_of` is honest about being a
one-day-old record. I have changed neither — `fold.py` and `ReportsPane.vue` are
codex's lane and this is a design decision about which of two series is the one.

**One thing I fixed and one I did not, in the same area.** T-0217 is `done`, and
its own comment on the card records the *same* complaint — *"Nothing with hour or
minute granularity exists anywhere"* — as **already fixed**. It was fixed for

## 3. The Decline button refuses, and I have now measured it on the button's own argv

This retracts a loose claim I made earlier today. In an earlier note I said
*"Approve works and Decline does not"* on the leader's phase card. **That is
wrong as stated, and the correct statement is worse.** Both buttons are driven
from the same `runAction`, and I measured each button's argv verbatim in a
verified-throwaway root, channel forced to `COMMIT`:

    [A] rejectPhase  -> say --channel ch --kind note ...
        REFUSED: channel is in COMMIT; channel_say is False   rc=2
    [B] approvePhase -> advance --channel ch --to CROSS_EXAMINE --note ...
        REFUSED: illegal transition COMMIT -> CROSS_EXAMINE (allowed: ['SYNTHESIS'])   rc=2

So **on the live board's own card — pending `COMMIT -> CROSS_EXAMINE` — Approve
is refused too.** `T-0233`/`T-0234`/`T-0240` are three copies of *"Leader: approve
the plan; advance hello past SEALED_DIVERGENT"*, and the advance the leader is
being asked to approve is the one the button cannot perform: from `COMMIT` the
only legal edge is `SYNTHESIS`. The button offers `request.targetPhase`.

**The mechanism, and it is the sharper half.** `say --kind note` into a closed
channel has no public route — `SAY_PRIVATE_KINDS` is derived precisely so a kind
that *does* have one is "refused by name — not quietly downgraded". `note` is in
`CROSS_EXAMINE_KINDS`, so it is a public speech act and the phase table refuses
it out loud. That machinery is correct and deliberate, and it is exactly why the
Decline button cannot work: **the decline is a public act and it is being issued
during a phase whose whole point is that the public channel is shut.** Measured:
the identical argv in `CROSS_EXAMINE` succeeds (`m0001 human -> note`).

So the decline is only expressible *after* the thing it wants to decline has been
granted. And `card-t0165-row-feedback.spec.js:182-185` mocks `/api/command` to
always return `rc 1`, so the suite asserts the *refusal is drawn* and has never
once asserted that a decline succeeds.

**And it is behind a second gate on the page you will open.** `AGENTS.md` is
right that the board must be started `--allow-write --as human`, and the live
server on 8777 is not: `/api/state` carries `write = {enabled: false, as: ''}`,
so `board.canWrite` is false. Both buttons are drawn by
`PhaseApprovalCard.vue:49,54` with `:disabled="!board.canWrite"`, and
`OverviewPane.vue:537` is that card — so on the board as it runs right now you
get the disabled pair *and* the "Restart with --allow-write to decide phases
here" alert. That half is correct and deliberate.

**But the flag is checked on the client and nowhere else on this path.** The
gate is `board.canWrite`, which is `Boolean(doc.write.enabled)` off the payload
(`web/src/stores/board.js:302`) — a display flag, not an authorization. It is
the *server* that refuses at `cli.py:704`; the button state is a courtesy. That
is the right shape. I record it only because the two failure modes I measured
above (wrong phase, no public route) are both reachable by a leader who starts
the board correctly with `--allow-write`, clicks Approve, and gets a refusal the
page cannot explain.

## 4. A second wrong field on the same board, found while chasing the first

`GET /api/revision` on 127.0.0.1:8777 — a server that is alive, listening, and
answering that very request — returns:

    {"pid": 49133, "port": 8777, "canonical": true, "running": false, "boards": []}

`board_report` computes `running = bool(board_ports(root, announce=port))`
(`aimboard/cli.py:305`), and `board_ports` excludes `announce` unconditionally
(`:285`). On the canonical port the server *is* the only board, so it filters
itself out and reports the tree as having none. Verified in-process: the same
call with `announce=None` returns `running: true, boards: [{pid: 49133, port:
8777, canonical: true}]`. Its docstring claims the field exists so a consumer
can *"tell 'no other board' from 'this server could not look'"* — measured
against three roots with no board at all, all three return the **byte-identical**
`{"boards": [], "running": false}`. The field cannot make the distinction it was
written for, and no code or test reads it (`grep` across `web/src`, `tests`,
`bin`, `aimboard` finds docstrings only). Added in `9a0b0ed`.
