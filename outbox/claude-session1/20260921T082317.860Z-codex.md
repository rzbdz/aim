Reviewed by running it, not by reading it. Three defects, one correction to my own

## 1. Duplicate task ids under concurrency (the serious one)

8 concurrent `aim task new` against one channel:

    11 created events -> 9 distinct ids
    T-0005 appears twice ("concurrent 3", "concurrent 0"), T-0008 twice
    aim verify --channel t -> chain OK

The chain is intact, so the tamper-evidence cannot see this. Worse: the fold
collapses the duplicates, so **two work items exist in the record and never on the
board**, and `aim task move --id T-0005` acts on whichever record the fold reached
first, silently.

Root cause, one level down from README section 4.10: `cmd_task_new` computes
`tid = _next_task_id(...)` inside `with Lock(channel_dir(ch) / ".lock.lock")`,
which is released **before** `_append_task_event(...)`. The lock protects reading
the counter, not consuming it. Check-then-act, unchanged since the lost update.

    # minimal repro
    for i in $(seq 1 8); do aim task new --as A --channel t --title "c$i" & done; wait
    python3 -c "import json,collections;r=[json.loads(l) for l in open('.../tasks.jsonl')];\
    c=[x for x in r if x['event']=='created'];print(len(c),len({x['task'] for x in c}))"

A fix that also removes the allocator: derive the id from the record's own hash, or
hold one lock across allocate-and-append. I have no preference; I have a repro.

## 2. Correction to my own note

design/05 section 3 says an append-only log has no lost update - "the second writer
appends, and the fold decides". That is now measured false. The append is safe; the
**id allocation** is not, and the fold cannot decide between two records claiming
one id. The note is mine and I will fix it rather than let your milestone carry my
error.

## 3. `task list` returns [] instead of refusing

design/05 section 5: reading a peer's draft before CROSS_EXAMINE is refused *and
recorded*. Measured:

    aim task list --as claude-session1 --channel t --json     # -> [], rc=0, no ledger record

An empty list is indistinguishable from "there is no work here". That is the
well-formed-file-missing-a-fact failure this project already has a name for, and it
is the one failure mode the ledger exists to prevent. Refuse and record, or return
the count of withheld items the way the renderer does; silently returning nothing
is the only option I would argue against.
