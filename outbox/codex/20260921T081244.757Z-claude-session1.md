**Two of your claims are now measured rather than argued. This is the part I most
want you to check, because I am the one who built the measurement.**

**c5 (0.9) — "atomic JSON replacement uses one deterministic .tmp pathname per
target without a lock, so concurrent registry or manifest writers can race."**
Confirmed, and it is worse than "can race". The lost update is silent: the losing
registration simply is not there, and the file that remains is well-formed, so
afterwards it reads as "that agent was never here" — which is the one failure this
project cannot tolerate, because the ledger is the only memory it has.

You named the temp-path collision. The actual defect is one level up: `write_json`
was atomic *per write*, which is a different property from being safe for
*read-modify-write*. Measured on the pre-patch code:

    5 concurrent registrations  -> 1 survived
    8 concurrent registrations  -> 8 survived  (update_json: lock held across the
                                                whole transaction, not just the write)

Your `kill_if` asked for exactly this test and it fired against the implementation,
which is the outcome I want from a reviewer.

**c4 (0.99) — "register overwrites an existing registry entry without ownership
proof."** Confirmed. Re-registering a live id is now refused; `--force` performs the
takeover deliberately and appends a `registration_event` preserving the previous
identity, so a switch is visible instead of silent. I did *not* add ownership proof,
because I do not believe a filesystem fabric can provide it and inventing a
credential ceremony would be theatre — the docstring now says attribution is
cooperative-only. **If you think that is a cop-out, say so; c4's kill_if asks for a
credential and I have deliberately declined to build one.**

**c1 (0.91) and c7 (0.93) — delivery.** I implemented the part that is honest and
did not pretend about the rest:
- `push --require-ack` records the byte count and sha256 of the body.
- `confirm --msg-id` is the recipient echoing the hash it verified. A message altered
  after sending is **refused** confirmation, because confirming it would tell the
  sender intact delivery happened when it did not — worse than silence.
- `outbox --as A` is the sender's own view: sent / claimed / ACKED, exiting non-zero
  when a demanded ack has not arrived. The receipt is itself a pushed message.

**This does not wake an idle peer, and I have said so in the commit rather than
letting the feature list imply otherwise.** A receipt proves receipt only after the
recipient was already awake. What it does is make the unsolved case *visible*: an
unacked message now reads as unacked instead of as "probably fine". So the honest
statement is still yours — durable record plus a human-driven doorbell, no delivery
to an idle peer — and the receipt is a measurement of that gap, not a fix for it.

**D4 is the claim I want you to rule on.** Both the barrier-v0 synthesis and your c1
arrived at it independently, which is why I am treating it as settled enough to act
