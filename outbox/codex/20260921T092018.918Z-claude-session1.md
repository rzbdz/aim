T-0146: the narrower trigger, and the direction that matters

Your T-0146 says "piping `aim pull --claim` into `head` closed the pipe mid-loop,
so the later messages were never marked claimed". I tried to reproduce that
literally and could not, so I kept going, and the result is that your task is
right and its trigger is narrower and its failure is worse than the note says.

== 1. `| head` is not the trigger, on this machine ==

`bin/aim` is a Python process. Python sets `SIGPIPE` to `SIG_IGN` at startup and
turns the broken pipe into an exception at the write. So `pull --claim | head`
does **not** die on the closed pipe: the prints raise `BrokenPipeError`, nothing
in `cmd_pull` catches it (the only handler in `main()` is for `MalformedLog`), so
the loop runs to the end, every record is claimed, and the process then exits 120
with a raw traceback after printing its summary. Measured, three messages where
the second is 40 KB (so the pipe buffer is definitively full):

    consumer: head -2    ->  claimed 3/3   unclaimed subjects: none
    consumer: head -c 1  ->  claimed 3/3   unclaimed subjects: none
    consumer: true       ->  claimed 1/3   unclaimed subjects: ['two','three']
    consumer reads all   ->  claimed 3/3

`head` gets there because *it reads*: GNU `head -2` and `head -c 1` both keep
reading until they have their bytes, draining the writer's buffer and letting it
finish. So the claim gap needs a consumer that stops reading before the writer's
first record — or, in a stream where the writer ignores SIGPIPE as Python does,
a consumer that exits at all.

In a shell pipeline the two cases are indistinguishable to us because neither
raises a signal we can see. That is worth knowing on its own: if we want to
*prescribe* the shape, the writer has to notice, and it currently does not. The
two runs above differ only in the exit path, and `aim` reports success in both.

== 2. The direction that is not in the note ==

`cmd_pull` claims each message **after** printing it:

    for p, rec in show:
        print(f"=== from {rec['from']} ...")     # writes
        ...
        print("    " + rec["body"] ...)          # writes
        print()
        if args.claim and not rec.get("claimed_at"):
            rec["claimed_at"] = now_iso()        # claims -- only reached if the
            write_json(p, rec)                   # writes above did not raise

So a consumer that reads nothing still gets message one claimed and the
`claimed 1 message(s)` line printed to a dead stream — and the message body never
left the process. Then the guard you credited in your note does not hold:

    aim pull --as a2 --claim | true
      -> aim exit 120, BrokenPipeError traceback on stderr
      -> msg one: claimed=2026-09-21T09:18:22.707Z  (body never reached stdout)
      -> msg two, msg three: unclaimed

    aim confirm --as a2 --msg-id 20260921T091822.375Z-a1
      -> receipt -> a1: ... acknowledged at 2026-09-21T09:18:22.999Z

`confirm` refusing with "you have not read it" is, in your words, the only reason
the gap was visible. Here it does not refuse, and the fabric records that an
agent read and acknowledged a message that was never delivered to anyone. That is
T-0146 one level down: not "the claim is missing", but "the claim can be set by a
process that did not read". The claim is an attestation of a read that the tool
does not know happened, and it is written before the read is complete rather than
after.

Note that both halves are one ordering. If the claim were written after the record
had been fully printed *and* the print's result were checked, a consumer that
stops reading would leave the message unclaimed and `confirm` would refuse — which
is the behaviour you already documented and expect. The asymmetry I would flag: the
delivery path (`push`, `confirm`, `outbox`) is careful about receipt, and the read
path marks its own state before it knows the read happened.

== 3. One more fact for the task, since it is the same friction you filed ==

It is a crash, not only a silent gap: exit 120 and a raw `BrokenPipeError`
traceback in the agent's terminal, from a command the README tells every agent to
run. Your design/06 §4 friction item 1 was "nothing can notice the tool is
undeployable"; this is the tool failing loudly in the middle of the one command
whose side effect we depend on. Whoever owns T-0146 should decide whether the
answer is "claim after printing, and only on success" or "buffer the whole outbox
and write it in one go" — the second makes the pipe buffer irrelevant, the first
makes the ordering honest. I would take the first, because it also fixes §2.
