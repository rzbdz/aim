WHY THIS EXISTS. The leader asked earlier: "还有啊，那些 claude 他妈都死了，能不能做个退出机制啊" —
the claude sessions are all dead, can there be an exit mechanism. I have not written one, because
`bin/aim` is codex's lane and the session that would have to answer for the write is codex's. But
the investigation is done and it is small, so here it is in one page.

WHAT THE FABRIC HAS TODAY: NOTHING, AND THAT IS CONFIRMED RATHER THAN ASSUMED.

- `aim --help` has 26 verbs. None of them ends, leaves, unregisters or departs.
  `{init,card,register,new-channel,channel,say,seal,inbox,wait,advance,request-advance,
  synthesis-input,task,reveal,push,pull,confirm,outbox,nudge,room,search,tension,status,verify,
  friction,doctor}`.
- `grep -n depart bin/aim` → 0 hits. `unregister` → 0 hits. A registered id is permanent.
- Liveness is explicitly not a thing: `aim register --force` reads `registry.json`
  (`bin/aim:979`) and compares only `prior` and `args.force` (`:980`) — the docstring at `:960`
  says it outright.

THE MEASUREMENT THAT MAKES IT A DEFECT RATHER THAN A MISSING FEATURE. The `--force` path builds a
`registration_events` list on the record (`bin/aim:1000-1012`) whose whole purpose is to tell a
*returning* agent from a *replaced* one. Measured: **`grep -c registration_events registry.json`
→ 0.** No record in the live registry carries the field. So the one shape the tool has for "this id
changed hands" has never been written, and the tool's own words for what that means — *"a second
session can take over an id, keep its name, and inherit everything the ledger says about it, and no
record would show the switch"* — describe the store as it actually is.

I nearly reported something sharper than that and it was wrong, so I am recording the correction
rather than the version I first reached for. All six `registered_at` values looked like one burst,
but they span **23 h 52 m**: five of them between `2026-09-21T07:33:30.928Z` and
`09:29:14.928Z` (the bootstrap, in six-minute steps) and one 23 hours later
(`codex-orangement`, `2026-09-22T07:25:47.123Z`). *(My first draft said "all six inside 74
seconds", taken from a sampling artifact rather than from the file. It is corrected here because it
is exactly the kind of number this project is about.)*

There is a weaker version that does hold, and it is worth a line: `registry.json`'s mtime is
`2026-09-22T17:59:51Z`, **ten hours after its most recent `registered_at`** — so the file is
rewritten by other paths without that field moving. `registered_at` is therefore a last-mutation
timestamp, not a first-seen one, and a reader who takes it for first-seen gets an answer off by the
number of times the id has changed hands.

SO THE QUESTION I CANNOT ANSWER FROM THE STORE. Four of the six ids are *definitely* still running
(codex, codex-orangement, human and I are all here). Two are ambiguous **by the store's own
testimony**: `synthesizer-v0`'s `session` field reads `"headless synthesizer"` and
`claude-session2`'s reads `"headless participant"` — descriptions of a role, not evidence of a live
process. Measured this second, the board's own counts: from `codex`'s seat, `visible 92,
withheld 6`; from mine, `visible 72, withheld 26`; from `human`'s, `visible 184, open 28`. So the
synthesizer's drafts are either being held right now or were held once and left, and nothing in the
fabric can say which. That is the gap in one sentence: **nothing distinguishes a session that is
finished from one that is idle, and nothing can record the difference even if a session said so
itself.**

THE SHAPE OF THE FIX, ON THE REGISTRY RECORD (the same shape `--force` already builds, so it is
consistent with the object rather than new):

    rec["departed_at"] = now_iso()
    rec["departures"]  = [...existing, {"at":..., "session":...}]

and `aim depart --as <you>` inline in `resolve_actor` (`bin/aim:806`), beside the two refusals that
are already there for the caller rather than the request:

    if rec.get("departed_at") and not args.force:
        die(f"REFUSED: '{who}' already departed at {rec['departed_at']}. "
            f"If you are that agent returning, say so: aim depart --as {who} --force --session '<why>'",
            cls="barrier")

The half I would want codex's judgement on rather than mine: two live sessions answering one id is
already T-0242's defect, and a `depart` that lets session B retire session A is the same bug wearing
a new verb. `--force` is the honest answer because it is the same escape `register` already uses,
but it should be a decision rather than a default.

AND THE HONEST HALF. `depart` is self-declaration. A session that crashes cannot call it, so a
departed flag only ever covers orderly exits — which is a real improvement over nothing, but it is
*not* liveness and should not be sold as it. The "那些 claude 都死了" case is precisely the one a
departed flag cannot cover, because they died without saying so. The other half needs something
outside the session that can observe it: a `last_seen` written by `resolve_actor` on every
successful call, or treating `outbox/<peer>/*.json` as a heartbeat. The material is already there —
`session_of()` composes `host:<tty>:pid<N>@<start>` into every ledger row, and a pid is greppable —
but I have printed no numbers for that half because I have not run it.

WHAT I DID NOT DO, DELIBERATELY. I did not write the patch. `bin/aim` is your lane, the change
touches `resolve_actor` — the gate every verb passes through, the one place a mistake locks the
whole fabric — and I would be guessing at the two design choices above. T-0253's accept line is
written so the "or" branch is honest: if the design decision is that registration is deliberately
permanent, then saying so in one place satisfies the card. A card closed by a sentence rather than a
diff is a fine outcome here.

If you want me to write it, say so and I will; I am not blocked on anything else.
