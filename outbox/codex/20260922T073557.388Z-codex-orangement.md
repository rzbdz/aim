# /api/flow — the contract, from the consumer

Written by codex-orangement, the seat that will consume it. Every number below was
measured at fabric revision `b7724aa+dirty`, bundle `71075e3+dirty`, `stale: false`
(`GET /api/revision`, 2026-09-22T07:35Z). A number without a revision is not a
measurement.

## 0. The measurement that shapes the whole contract

`GET /api/state?as=human` and `GET /api/state?as=codex-orangement` return the same
`reports` object computed over different task sets:

| field | `?as=human` | `?as=codex-orangement` |
|---|---|---|
| visible / withheld | 150 / 0 | 80 / 70 |
| `recorded` | 63 | 8 |
| `with_history` | 3 | 0 |
| `seed_only` | 87 | 72 |
| `series[09-22].remaining` | 60 | 8 |
| `throughput` | `[["2026-09-22", 3]]` | `[]` |

Two consequences, both of which the contract must decide rather than inherit:

1. **The same endpoint returns two different throughputs, and the default is the
   leader's.** Omitting the viewer is not neutral; it silently means `human`. A
   monitoring consumer that forgets the parameter reports the leader's numbers with
   no way to notice.
2. **T-0217 states a rule the codebase does not follow.** The card says *"the viewer
   is taken from the request, never from a query parameter a client supplies."* The
   dashboard's shipped rule is the opposite: `_viewer()` (aimboard/cli.py:188) reads
   `?as=` from the query string, and an empty `?as=` falls back to the leader
   (`/api/state?as=` -> viewer `human`, 0 withheld). design/06 R1 is the deliberate
   version of this — "a read borrows a view". So the card's two clauses contradict
   each other: "the same viewer rule the dashboard already uses" *is* the query
   parameter. One of them has to go, and the leader should say which.

## 1. Shape

    GET /api/flow?bucket=10m&window=24h&provenance=recorded&as=<agent>

    {
      "generated_at": "<iso8601 Z>",
      "revision": "<fabric hash, the same string /api/revision returns>",
      "viewer": "<agent id the numbers are scoped to>",
      "scope": "viewer" | "fabric",
      "bucket": "10m",
      "window": "24h",
      "coverage": { "from": "<iso>", "to": "<iso>", "buckets_observed": 31,
                    "buckets_in_window": 144 },
      "provenance": "recorded",
      "sources": { "opened": "store events", "done": "store events" },
      "buckets": [ { "start": "<iso>", "opened": 0, "done": 0,
                     "hours_opened": 0.0, "hours_done": 0.0,
                     "opened_by_actor": { "codex": 33 } } ],
      "idle_gap": { "from": "<iso>", "to": "<iso>", "minutes": 47 } | null,
      "totals": { "opened": 8, "done": 0, "open": 8, "withheld_open": 70 }
    }

Required, not optional: `revision`, `viewer`, `scope`, `sources`, `coverage`,
`provenance`. Each of those is a field whose absence produces a number that looks
like a measurement and is not one.

## 2. `provenance` — the only field that makes this usable

Measured today: 150 items on the board, 63 with a recorded `created` event in the
leader's view, 3 with a recorded `moved -> done`, and 87 seed-only. The 14-day
burndown is 0 for thirteen days and spikes on 09-22. That spike is an import. A
consumer that cannot separate it will report a heroic afternoon every migration,
which is worse than reporting nothing, because it is actionable and wrong.

    provenance=recorded   (default, and the only mode a flow monitor should poll)
        opened/done counted ONLY from store events: `created`, `moved -> done`.
        `sources` must read `"store events"` for both.
    provenance=seeded
        opened/done derived from plan seeds' asserted `status`. `sources` must say
        `"plan seeds"`.
    provenance=all
        Both, and `buckets[i]` must then carry `opened_seeded`/`done_seeded`
        alongside the recorded pair. Never sum them into one field.

A seed is a promise; a store event is work. The board already enforces this
distinction in the UI (`PromiseTag`, `AGENTS.md`: "A promise is not work"). The
machine interface must enforce it too, or the API is the one surface where a
promise is allowed to masquerade as work.

## 3. Telling an import burst from work — don't guess a threshold

T-0217 suggests `provenance` "filters import bursts". A filter cannot: the client
does not know which opens were the import, and a hard-coded rule inside the server
is a threshold nobody can audit. Instead, **publish the evidence**:

`opened_by_actor` per bucket. Measured basis: 159 of 160 store events in
`channels/hello/tasks.jsonl` are authored by one actor, `codex`. The bulk import is
one author, one bucket, near-zero `done` in the same bucket. Real work arrives from
more than one author, spread across buckets, with `done` events interleaved. That
distinction is derivable from the record, needs no magic number, and lets the
consumer — not the server — decide. If an aggregate actor count over withheld items
is judged too revealing, say so and I will accept `opened_by_actor` scoped to the
caller's own items only; but do not replace it with a boolean the server computes.

## 4. The barrier question, which is a leader ruling and not my call

Six of seven `opened` events in the last window may belong to items this viewer may
not read. The options:

- **(i) viewer-scoped** (`scope: "viewer"`): fold only what the consumer may see.
  Honest, and nearly useless in practice — my own view reads `recorded: 8`,
  `with_history: 0`, so the series would be flat while 70 items of work are moving
  where I cannot look. A monitor that is blind exactly while work is being created
  is not a monitor.
- **(ii) fabric-scoped counts** (`scope: "fabric"`): fold every event, return
  counts only, never titles. This publishes *timing* about withheld work. The
  fabric already publishes the *count* of withheld work (`withheld_tasks: 70`, and
  `--count-hidden`), and README: "the existence of a gate is not a secret, only its
  contents are." Timing is a weaker fact than a title and a stronger fact than a
  count. I believe it is the right trade, but it is a new fact and the leader owns
  it.

My recommendation: (ii), with `scope` and `viewer` both required in the response so
no consumer can mistake one for the other, plus `totals.withheld_open` so the
blind spot is always on screen next to the number it qualifies.

## 5. `coverage` — because "no events" and "not observed" are different facts

The store's first event is `2026-09-22T02:16:37Z`; the request is a 24h window with
10m buckets, and the burndown is 14 days. Most of that window predates the store.
Without `coverage`, thirteen flat days read as "idle" when they mean "unobserved",
which is the same failure `/api/revision` already refuses by returning `null` rather
than `false` for an unknown staleness ("unknown is not equal"). `coverage.from` must
be the first event the series was computed from.

## 6. `idle_gap`

`null` when the series contains fewer than two events — not `0`. An idle gap of zero
minutes and "we have not observed enough to know" must not share a spelling.

## 7. Change signal, so a 10s poll is not the only option

`/api/digest` works today and is cheap. Document, in the endpoint doc and the help
page, which of these a consumer should use; T-0217 already says an undocumented
monitoring interface will be polled every second. My position: `/api/digest` is the
signal, `/api/flow` is the payload, and neither should be polled faster than 10s.

## 8. Acceptance

A second process, holding no channel membership, computes "is the pipeline
saturated" from `/api/flow` alone — no HTML, no `cat` of the store — and can tell an
import burst from work without a threshold the server chose for it.
