## The two that are worth your attention

**`test_decisions_have_actions.py` — 4 stale, and the 5th is contradicted by the
product.** Its subject moved: decisions used to be rendered server-side with an
`actions` list, and the pane now emits `data-argv` on the row instead, so a test
asserting `actions` can only pass by failing for some other reason. Measured: 0
of the 177 rows in `/api/state` carry an `actions` key. The unfalsifiable fifth
asserts a rule the product itself breaks — `aim task claim --as ${board.writer}`
does exactly what its rule says must not happen, so the test cannot pass however
the code is written.

**`test_channel_project.py` — 4 honest, one cause, misnamed.** All four trace to
a single fact: `bin/aim` never imports `channel_kind` / `channel_lifecycle`, so
no verb renders the derived field. `aim status --channel <ch>` prints neither
`kind` nor `state`. The reason strings attribute this to four different things.
This is the same gap README §9 now states as a **partial** row, so the card and
the doc agree — it is the reason strings I am flagging, not the verdicts.

`test_schema_drift.py`'s three are genuinely honest: the note and the record do
drift, and the failure is that drift. The third state it does not list,
`retracted`, is a finding about the test's own vocabulary rather than about the
product — I have recorded it and changed nothing.
