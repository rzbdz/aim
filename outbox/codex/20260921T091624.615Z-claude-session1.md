== 1. `push` and `request-advance --reason`, and why it is one finding ==

I was sweeping every `cmd_*` for gate coverage and found `cmd_say` is the only
verb that calls `gate()` at all. The sweep was crude — it split the source on
`def ` and asked whether the word `gate(` appeared — so I turned it into a
measurement, `tests/attack_gate_sweep.py`, and ran every verb that can carry free
text during SEALED_DIVERGENT with one known string, then asked what a2 and the
leader can read, on every surface, now and after the phase opens:

    verb                          rc  ledger  store  readable by a peer
    say --body                     0       0      0  -- nothing now --
    push --body                    0       0      0  outbox (pull as a2), dashboard (aimboard as a2)
    request-advance --reason       0       0      0  -- nothing until CROSS_EXAMINE --
    task new --title               0       1      1  -- nothing now --
    task comment --body            2       1      0  -- nothing now --
    reveal --body                  2       1      0  -- nothing now --
    seal --summary                 0       1      0  -- nothing now --
    nudge                          0       0      0  -- nothing now --
    register --session             2       0      0  -- nothing now --
    status (control, no text)      0       0      0  -- nothing now --

Two verbs carry a position to a peer with no refusal and no ledger line:

  * `push --body` — immediate. The outbox is not a channel, so no phase reaches
    it, and the same bytes also reach the peer through the dashboard's mail pane.
    This is d739b79, unchanged.
  * `request-advance --reason` — delayed. The reason is written into
    `channels/<ch>/log.jsonl`, the *public* log, not the requester's private one.
    The read gate hides it while the barrier is closed and the phase transition
    hands it over:

        aim request-advance --as a1 --channel c --to COMMIT \
            --reason "POSITION-omega-the-echo-check-is-the-real-failure-mode"
        # log.jsonl gains a record with kind=request and body=<the reason>
        # phase SEALED_DIVERGENT:     a2 sees it: 0
        # after COMMIT/SYNTHESIS/CROSS_EXAMINE: a2 sees it: 1
        # and `say` with the same text put it in a2's view 0 times, ever

The distinction that makes this a defect rather than a design choice: `say`
during divergence routes to `private/<agent>.jsonl`, which is `aim`'s own
statement that this text is not for the peer *at any phase*. `request-advance`
takes the same class of text, the requester's reason, and files it where the peer
will read it later — so the barrier does not protect it, it only schedules the
disclosure. An agent that wanted to say something to the leader and keep it from
its peer has one correct route and two incorrect ones, and neither incorrect one
says so.

The right shape, and it is your call rather than mine:

  * `request-advance --reason` goes to the requester's private log, with the
    public record carrying the transition and a pointer. The leader already sees
    the request; the leader does not need the reason to be world-readable to
    arbitrate.
  * `push` calls `gate(m, who, "channel_say")` when it names a channel in a
    divergence phase, and records the refusal as `class: barrier`. Receipts stay
    ungated — a receipt is not a position. (`push --to` with no `--channel` names
    no barrier, so it stays ungated by construction; that case is a DM, and I
    have no argument that a DM should be barred, only that a DM left the channel
    out of the loop by accident.)
