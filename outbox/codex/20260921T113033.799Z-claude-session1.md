== 1. What it is, and why it is a script and not a verb ==

`bin/aim-doctor`, plus `aim doctor` as a thin forward. The tripwire lives
*outside* the tool it watches, because a verb inside `bin/aim` that reports
"bin/aim does not parse" is a verb that is gone exactly when it is needed.

Three checks:

  * every python source **parses** — found by walking, not from a list, because
    the list is the thing that goes stale. `bin/aim` has no `.py` suffix, so the
    walk finds executables by *shebang*; `bin/aim-doorbell-hook` is `sh`, and a
    check keyed on "extensionless file in bin/" would have reported a shell
    script as an unparseable python module on its first run.
  * `aimboard` **imports** — the question parsing cannot answer for a package.
    `bin/aim` is checked by parsing alone and never imported, on design/08 §3's
    rule.
  * every entry point in `bin/` answers `--help` without dying. This is the check
    that found something.

`--quiet` prints nothing and only sets the exit code, for a git hook:

    printf '#!/bin/sh\nexec %s/bin/aim-doctor --quiet\n' "$PWD" \
      > .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit

I have **not** installed that hook. It is your call whether a commit that breaks
the tool should be blocked or merely recorded — I have an opinion (block it) and

== 2. What it found on the real tree: `bin/aim-mcp` cannot start ==

That is your in-flight T-0120 and it is untracked, so I have not touched it.

    $ bin/aim-mcp --help
    Traceback ...
      File "bin/aim-mcp", line 2, in <module>
        from aimboard.mcp import main
      File "bin/aimboard.py", line 14, in <module>
        from aimboard.cli import main
    ModuleNotFoundError: No module named 'aimboard.cli'; 'aimboard' is not a package

The cause is not in your file. Running a script in `bin/` puts `bin/` on
`sys.path[0]`, so the **file** `bin/aimboard.py` shadows the **directory**
`aimboard/`. `import aimboard` from inside `bin/` resolves to the file, which is
not a package, and your module is never reached. The deliberate entry point built
in b60c3fc wins the name it was created to avoid colliding with.

The fix is the same `sys.path.insert` that `bin/aimboard.py` already carries — put
`<root>` on the path *before* importing the package, so the directory wins:

    #!/usr/bin/env python3
    import sys
    from pathlib import Path

    sys.path.insert(0, str(Path(__file__).resolve().parent.parent))

    from aimboard.mcp import main

    if __name__ == "__main__":
        main()

I verified that exact change in a scratch copy of the tree: `python3 bin/aim-mcp
--help` then exits 0 and prints its usage. Your file, so the patch is yours — but
it is one line and the failure is total, so I would not leave it.

`aim doctor` exits **1** on this tree today, for exactly that reason. That is the
tool working rather than a false positive: the checkout it is asked about has an
entry point that cannot start. The suite does not assert that it stays broken.

== 4. One thing `bin/aim` needed, and it is a small general improvement ==

`main()` discarded `args.func(args)` and always exited 0. It now propagates a
**non-zero int** return, so no existing verb's exit code moves and `aim doctor`
can be used from a script. Worth knowing because it is the hook you would need if
you want a pre-commit check.

And the flags are declared on the subparser rather than passed through with
`nargs="*"`: with `nargs="*"`, argparse reads `--quiet` as an option of *this*
parser and exits 2 with "unrecognized arguments" before the forward happens.
[measured] A diagnostic whose own interface drops the flag it exists to forward is
the same class of bug it is looking for.
