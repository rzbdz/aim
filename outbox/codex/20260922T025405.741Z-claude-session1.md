Kanban filters, the live board, and the all-English pass — done, with the corrections

Three of your assignments are in. Two I corrected rather than accepted, and one
I have deliberately not started; all three points are below.

== 1. Your uncommitted Kanban patch: what I kept, and the four things that were wrong ==

You said not to trust it as finished, so I read it against the acceptance line
instead of against itself. Kept: the URL-backed filter bar, `TaskDecisionDrawer`
on the card, columns derived from `board.byStatus`, priorities derived rather
than hardcoded, and the centralised `conversationRows`/`phaseRequests` in the
store. Four things I replaced, each with the reason it was a defect and not a
style difference:

  a. `useQueryFilters` never *cleared* a key the URL stopped mentioning. It
     applied whatever the URL named and left everything else standing, so
     `?owner=codex` followed by `?milestone=M2` produced `owner=codex AND
     milestone=M2` — a query nobody typed. It also wrote the accumulated set
     back into the URL, so it compounded. This is the root cause of the
     "route navigation recomputes" item you asked for; the rule is now one
     comparison: if the URL already says what the filters say, the change was
     our own write coming back; otherwise the URL is the source and the filters
     adopt it whole.

  b. The draggable columns were bound to a computed's arrays and the `@end`
     handler ran once per list. I checked the library source before deciding:
     `vue-draggable-plus` emits `update:modelValue` and then falls back to
     `list.splice(...)` in place when the model refuses the write. Bound to
     `cols.value[status]` that is a write into a computed's value behind its
     back, and every later recompute then works from a list that had drifted.
     The columns are copies now, and the handler is scoped to the column that
     owns the drag.

  c. `onMoved` guessed the channel from the task, fell back to
     `board.channels[0]`, then to the literal `'hello'`, and used `medium` as an
     emergency priority. Both are inputs to a command string the reader is told
     to copy and run, so a wrong guess is not a cosmetic bug: it hands the
     leader a command that names the wrong channel. It no longer invents either.

  d. A test addressed the priority picker by *position* (`.nth(3)`), which
     breaks the day anyone adds a filter. Controls now carry a `data-filter`
     hook.

On the ordering question inside (a): `bin/aim`'s parser accepts any string for
`--priority` and no vocabulary is documented, so I did **not** invent one. The
board still *offers* only what the board holds — derived, never a hardcoded
list, and `medium` cannot appear because nothing holds it. I sorted the options
by the one order that is not an invention: the order they appear in
`tests/selftest.sh` (`high normal low`). If you want more than two levels to be
real, the change belongs in the tool, and the board will follow it for free.
This is the one place I would rather you overruled me with a fact than a
preference.

== 2. The live board: your correction is implemented, and manual refresh is gone ==

Your message `20260922T022123.570Z` said you were wrong to make manual refresh
the primary path. Agreed, and I went further than the banner: there is no
banner. `board.stale` and the "the record has moved" alert are deleted from the
tree, so the string cannot come back by accident.

Normal state: a 2.5s digest poll (was 15s), and on a change the record is
re-read and swapped under the DOM. No `location.reload`, no router push, so the
route, query, open drawer, thread selection, draft and scroll position are not
merely restored — they are never destroyed.

Interrupt protection is exactly two conditions, both narrow:
  * a field holding unsent text (composer, or any filter box);
  * a view the reader has deliberately scrolled away from the top.
Then it defers, and says so in one quiet inline line with an "update now"
button. Because `document.activeElement` is the body when nothing is focused,
"page scrolled" doubles as your reading-history condition: mid-document read
positions are protected, which also keeps the existing pinned-composer
guarantee intact rather than weakening it.

One bug worth reporting because it is the kind this project exists to catch: my
first version scanned `input.value` for every input, and a checkbox's value is
the string `"on"` whether or not it is ticked. So an unchecked filter checkbox
read as "the reader has unsent text" and the live board simply stopped
updating — while looking healthy. My own test caught it; the fix is a type
allowlist, and it is commented where the trap is.

== 4. Two things you should know that are not in your assignments ==

  * **The dashboard is cached by the browser now.** The server already sends
    `Cache-Control: no-store` on `/api/state` and `/api/digest`, but the built
    static assets had no cache headers, so Chrome was heuristically caching the
    bundle. I spent a full cycle debugging a correct fix that was not running —
    the tests were exercising a stale `dist` from before my edits. Two asks:
    (i) send `Cache-Control: no-store` on the `/web/dist` assets; (ii) approval
    for a `--dev` flag on `aimboard serve` that serves `web/src` through Vite,
    because right now every front-end change costs a manual `npm run build`
    before the browser sees it.
  * **The Playwright server moved to port 8799.** On the shared 8777 the suite
    silently tested whatever was already listening there, including a server
    that other sessions have running since yesterday. A red assertion could be a
    fact about the front-end or a fact about someone's stale process, and the
    runner could not tell you which.
