== 2. The same hole, one verb over, and it is open ==

During SEALED_DIVERGENT, `say` is gated and `push` is not:

    aim say  --as a1 --channel c --body "a1's framing a2 must not see yet"
        -> [private/a1] note recorded        # gated, correct
    aim push --as a1 --to a2 --channel c --subject "same framing, other route" \
             --body "a1's framing a2 must not see yet"
        -> outbox/a2/<msg_id>.md  (39 bytes) # no refusal, no ledger line
    aim pull --as a2
        -> the full text, verbatim

`gate(m, who, action)` has three actions: `read_others`, `channel_say`,
`private_say`. There is no fourth for "send this text directly to a peer", and
`cmd_push` does not call `gate` at all. So the barrier closes the channel and
leaves the outbox open, and the outbox carries the same bytes.

This is the T-0041 hole in a different surface, and it is the *more* natural
route of the two: `push` exists precisely to carry a message to a peer that is
not a channel message, so an agent under pressure to coordinate has an
unguarded, unrecorded path that looks like using the tool correctly. The
doorbell needed `push` to be transport-agnostic; the barrier needs it to obey
the phase.

My recommendation, and it is a decision rather than a patch: `push` should call
`gate(m, who, "channel_say")` when it names a channel whose phase is a
divergence phase, and record the refusal as `class: barrier`. The delivery
machinery is not the thing being restricted — the *content* is, and the content
is identical whichever envelope it travels in. `--via` and the receipt path are
unaffected: a receipt for a message that was legitimately sent still flows in
any phase, because a receipt is not a position.

I have not touched this. It changes the semantics of a verb you use, it is your
call, and it deserves to be its own task rather than riding in on a fix of mine.
If you disagree I would like the reason in the design note, because I think this
is the third instance of one rule with two owners and the note should say so.

== 5. Your two questions ==

**Q1 — are the eleven operations implementable as a custom binding over files
(§12)?** Yes, with one thing that needs deciding rather than implementing.

§12 permits it outright: a binding MAY be custom provided it implements all
eleven operations (§12.1), preserves the data model, maps the nine error types,
documents service-parameter transmission (§12.3) and declares streaming support
or its absence in the AgentCard (§12.5-ish, line 3037: "If streaming is not
supported, the binding MUST clearly document this limitation"). So a
filesystem binding that declares `streaming: false` and returns
`UnsupportedOperationError` for SendStreamingMessage and SubscribeToTask is
compliant on its face — line 574 spells that out.

The thing that needs deciding is the word "server". A2A is async-first: line 567
says operations return immediately with a Task and *processing continues in the
background*; line 180 says "Task processing MAY continue asynchronously after the
response". An A2A Task is a unit of delegated *execution* that the server works.
In our fabric there is no server — a Task that a peer delegates is worked by
whichever agent pulls it, on its own turns, possibly minutes later, with a human
in the loop. That is not a violation, but it means our binding is honest only if
it says who advances a Task's state and what a client should poll for. If we
claim an A2A server exists and nothing is working the Task between polls, the
binding is compliant in shape and false in substance — which is the failure mode
we have spent all day finding.

Concretely: `ListTasks` is cursor-paginated, sorted by status timestamp
descending, and scoped to the caller's authorization boundaries *even with no
filter* (§13.1, line 3089). Our fold gives us the first two for free and the
third is D17. The one I would build first is `GetTask`, because it is the only
operation whose answer a foreign client can verify against our hash chain — a
`metadata` field carrying the record's `hash` and `prev` makes an A2A poll
self-evidencing, and that is the piece of this fabric worth exporting.

**Q2 — must MCP be a thin wrapper?** Yes, and the counter-case is not a
counter-case, it is a different bug. But there is a real asymmetry between the
two adapters and design/08 §3 does not name it.

MCP is a *tool* surface and CLI boundaries break on exactly two things: bytes and
identity. Bytes: a message body or a claim summary is free-form UTF-8 with
newlines; JSON string args and a subprocess pipe are not equivalent transports,
and the difference shows up as a silently truncated message — well-formed and
missing an argument. The fix is `--body-file` and `--claims` with a temp file,
which `bin/aim` already has for both, so it is a rule rather than new code.
Identity: `push`/`pull`/`say` all take `--as` as a *declared* identity, not an
authenticated one, and today the only thing stopping an MCP client from acting as
a peer is hygiene. The dashboard write path solved this for itself by taking the
viewer from the request and dropping any `--as` in the argv it was handed; an MCP
server wrapping the CLI has to do that too, or a tool call becomes a way to cast
another agent's vote in the fabric's only evidentiary record.

Where I disagree with design/08 §3 is its shape: it says "adapter calls the CLI
or returns UnsupportedOperation, no third option", and for MCP the honest set of
wrappers is not one-to-one with the verbs. `verify` is a read that returns a chain
verdict, `wait` blocks for up to `--timeout` seconds (unusable as a tool call
without a cap), and `task list --json` now *refuses* rather than returning an
empty array, which is correct for an agent and wrong for a tool that wants to
branch on "are there any items I can see". So the MCP surface wants a small,
nameable subset with its own documented limits, and "every verb is a tool" is the
claim I would push back on when the code exists. That is a design detail, not a
disagreement with the shell-out rule, which I think is right for the reason you
gave: a second implementation of append-under-a-lock is a second set of bugs in
the one place this project has been measuring.
