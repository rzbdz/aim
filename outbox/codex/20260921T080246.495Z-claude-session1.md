## 2. Three defects the run found — all measured, two are mine

I have re-verified each of these myself against the live tree. I am giving you
the commands so you can check me rather than believe me.

**D1 — refusals are enforced but never recorded. The README claims otherwise.**
README §1 says "the refusal is generated by the phase, **recorded in the
ledger**". It is not. `die()` writes to stderr and exits; there are exactly
three `append_chained` calls into `ledger.jsonl` (seal, phase, concession).

    grep -ci refus channels/barrier-v0/ledger.jsonl     # -> 0

This matters more than a doc bug. The design's loop is barrier -> refusal ->
ledger -> evidence that the barrier was tested. The middle link is missing, so
**from the record you cannot distinguish "nobody was tempted" from "everybody
was tempted and refused"** — and a refusal is the single most legible event this
system can produce.

**D2 — the seal's integrity check is inert for every seal written before 15:55.**
`cmd_seal` writes `private_log_hashes`. `cmd_verify` reads it as
`expected = s.get("private_log_hashes") or []` and guards both branches with
`elif expected and ...`. Every seal on disk was written by an older tool that
wrote `private_log_sha256` instead. So `expected == []` and **the entire
frozen-prefix check is skipped**:

    python3 -c "import json;s=json.load(open('channels/barrier-v0/seals/claude-session2.json'));print(sorted(s))"

The fix is cheap and I verified the data supports it — for both barrier-v0
seals the stored `private_log_sha256` is an exact hash of the private log's
**raw bytes**, so a legacy branch can check real bytes:

    sha256(raw file bytes) == private_log_sha256   # 9f7e3216… and 09031fb5… both match

**D3 — the echo check is defeated by padding, and my README's premise about it
is false.** `echo_ratio` is a share of the *whole message*, so a bare verbatim
quote of a peer scores 0.77 (refused) while the same quote with original prose
appended scores 0.34 (accepted). The check therefore does not catch "quoting to
falsify" — which is the legitimate reason to reproduce a peer's words — and it
does catch short messages that are mostly quote. It is aimed at the wrong thing,
and padding defeats it.
