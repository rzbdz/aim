position and sealing, work items, the human's half, how it ends, N agents, N
projects. I re-ran every claim marked **[V]** myself on a throwaway root before

| mark | means | survives |
|---|---|---|
| **ENFORCED** | the tool refuses, exit ≠ 0, writes a refusal row | a careless or hostile actor |

| **PROSE** | a document says so and nothing reads it | nothing |

Parts I and II walk one project from `aim init` to the end, then N agents and N
projects, marking every step. Part III is the methodology — six rules for

## The four measurements worth your attention

**1. A second project silently drops the first project's work.** A task id is
allocated per channel (`bin/aim:1832`) and the board merges every channel into
one dict keyed by that id (`aimboard/fabric.py:281`). Measured: two channels,
one `aim task new` each, both get `T-0001`, and the board then holds **one**
task — `{'T-0001': 'B work'}`. Either half alone is defensible; together they are
data loss with no warning. This is the clearest answer to "can this host more
than one project".

**2. The exemption is `kind == "human"`, and `kind` is self-declared.** Registered
`otherhuman` with `--kind human` — not the leader, not a participant, not the
owner — and they submitted another agent's card to `review` **and** approved it
to `done`, with **zero refusal rows**. The code comment at `bin/aim:2126` says
*the leader* is exempt. The same field is the board's read-side leader predicate
(`aimboard/gate.py:159`, `aimboard/views/chat.py:25`), so both surfaces agree on
a value neither verifies.

**3. The SYNTHESIS quorum checks that a file exists, not that anyone sealed.**
`bin/aim:1476` tests `(channel_dir / "seals" / f"{p}.json").exists()`. Measured:
hand-write `seals/gamma.json` as `{"agent":"gamma"}`, advance, and the phase
moves to `SYNTHESIS` with no `seal` ledger row for gamma and an empty private
log. `aim verify` afterwards says `TAMPER … carries no digest` and `chain
BROKEN` — the after-the-fact check works, nothing blocked it at the time. A
synthesizer can be handed a bundle containing a participant who never sealed.

**4. On the board as it is running right now, your approval button is disabled.**
`/api/state` carries `write = {enabled: false, as: ''}`, so `board.canWrite` is
false and `PhaseApprovalCard.vue:49,54` draws *approve* and *decline* both
disabled. The attention pane holds two pending `request` rows, one stale and one

## What the SOP says the goal needs

Nothing in `SOP.md` proposes a change; every row is a `file:line`. But the
judgement at the end is this: **the core is sound and the ceremony around it is
not.** Three mechanisms are real — the phase gate refuses and records (137
`barrier` + 126 `form` refusals in the live tree, each with a reason), the seal
chain detects tampering after the fact, and the task actor rules do stop a
bystander from submitting another's card. What is not real is the layer that
makes them mean something: a quorum a hand-written file satisfies, a claims
schema nothing validates, an exemption any name can claim, a terminal status a
card can be born into, an id space that merges two projects into one, and an end
state nothing asks for.

Ten rows, one shape — **a rule that reads as enforced and is only written
down.** That is the failure the barrier was built to catch, one level up.
