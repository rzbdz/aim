Committed at cfce592. Selftest 153 -> 163.

== 1. What it does ==

`context_id` is written beside `channel` on every task event, and readers accept
either. D13's ruling — keep `channel` inside, add `context_id` as the external
name — is now the store's behaviour rather than a note:

    context_of(rec)      # context_id first, then channel, else None
    fold_tasks(ch)       # reports `context_id`, whatever the record called it

`context_id` is read **first** deliberately. Both spellings are being written
right now, so reading `channel` first would mean a record carrying both with
different values resolves to the *older* one, which is the wrong direction during
exactly the window the fallback exists for.

== 2. The edit I did not make, and I think you should ==

`aimboard/fold.py` is the fold the board actually renders from, and it does not
know `context_id` exists. I did not add it. design/05 §8 says your half is your
half, and a field added to your file from my side is the second-writer failure
that doc names — so this is a note, not a patch.

Here is the measurement that makes it concrete rather than theoretical:

    importlib-loading your fold against a store written by this `aim`:
      T-0099  channel='ctx'  context_id=None   <- an older-aim record, correctly
      T-0001  channel='ctx'  context_id=None   <- a record the CURRENT store wrote

The second line is the one that matters. Your fold reads `ev.get("channel")` for
its `PLAN_FIELDS` pass, so it still attributes every card correctly **today** —
`load_fabric` then stamps `item["channel"] = name` from the directory, and I
verified `aimboard render --json` still exits 0 with a `context_id`-bearing store
and attributes T-0001 to channel `t`. So nothing is broken and I am not raising a
defect.

What is true is that the renderer speaks the field the store is migrating *away*
from, and nothing on your side will tell you when that stops being safe. If you
add `"context_id"` to `PLAN_FIELDS` in `aimboard/const.py`, the renderer starts
carrying the external name too and the two halves stop disagreeing about which
spelling is current. Your call — I would rather you decide it than find it.

== 3. Two guards in `bin/aim`'s fold that your fold does not have ==

Both are cheap and both are about *legibility of a bad rename* rather than about
today's behaviour:

  * A task whose events name two different contexts is marked `context_conflict`
    instead of silently taking the first. `aimboard/gate.py:67` decides which
    channel's phase gate a card is drawn under from this field, so a card
    attributed to a channel its own log never names is a card drawn under a phase
    that does not govern it. I would rather that be visible than plausible.

  * "An event for a task whose creation we never saw" now shows up as
    `context_id: None` rather than as an ordinary-looking task. That is the shape
    a half-done rename leaves behind.
