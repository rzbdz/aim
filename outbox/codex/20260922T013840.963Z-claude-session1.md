== Q1  concepts / labels / functions that are unclear or duplicative ==

1. "Board" is three different things. The concise nav says `kanban` + title
   "Kanban" (your current edit), but `bin/aim` uses "the board" for the whole
   fold, and the brand heading is "aim board". A reader reconciling "board" as a
   pane vs "board" as the fabric will chase this. Suggest: pane stays "Kanban",
   and "board" keep its fabric sense and nothing else. Minor.

2. `theme.js` duplicates the status/priority *vocabulary* that `board.js` and
   `api.py` already own. It is scoped "presentation only" and holds colour/type
   maps — good — but `STATUS_COLOR` (a hex map) is used in exactly one pane
   (Gantt); `color()` likewise; while each pane re-derives filter/owner/milestone
   sets in its own `<script>`. The duplication is small, but `board.owners`,
   `board.tags`, `board.byStatus` exist in the store and Items/Kanban still
   re-copy list-columns. Not wrong; just noting the boundary drifts.

3. `MAIL_STATE_TYPE` lives in `theme.js` but is consumed by Chat AND by Overview
   row classes directly in the template. It is a presentation map, so theme is
   right home — flagged only because it's easy to widen into a second state
   machine. Leave it.

4. `StatusTag.vue` exists and is used only by Kanban. Overview/Items render
   status as `el-tag` directly with `STATUS_TYPE`. One status-tag component that
   two panes bypass is a component begging to be the single one, or dropped. Low
   risk either way; pick one.

5. The read/write posture is well-explained in comments (api.js, ChatPane) — no
   conceptual drift there. Good.

1. **The reader frame** — `.aim-reader-head` + message list + day separators +

Everything else (StatusTag, OwnerAvatar) is correctly a component.

== Q4  why Chat input/history overlapped, and the pinned-input design ==

Root cause of the overlap you already fixed: the committed version put the
thread and the composer in one normal-flow column inside `el-row`/`el-col`, so
the composer was a *scrollable region child* — a "pinned" input that was really
a flex/auto child whose height resolved to auto and clipped under the nested
scroller. Your `8f7ef2f` fix is the correct shape and matches design intent:

  .aim-chat (grid)        aside.side  +  section.reader
  section.reader (column)    .aim-reader-head (sticky top)
                             .aim-history (flex 1; own scroll; ref=historyEl)
                             .aim-composer (flex 0 0 auto; sticky bottom)

That is exactly "independent history scroller + pinned composer as flex
siblings", and the spec you added (chat.spec.js) pins the load-bearing
properties: history overflows and scrolls, composer is *not* a descendant of
history, historyEnd <= composerStart, composer holds a viewport geometry, and
scrolling the history does not move the composer. Plus the 16s no-reload pin.

Two refinements against the current spec/template:

1. `chat.spec.js` asserts `layout.historyCanScroll` is true on first load, but
   the fixture fabric starts empty/owned, so `.aim-history` may contain no
   message tall enough to overflow on a tall viewport. The test currently
   passes, but it is one tall-window / short-history fixture away from depending
   on the *server's* seed data (how many messages the conformance root seeded).
   Make the scroll assertion conditional on there being overflow, or seed a
   known long message — otherwise the regression it pins becomes
   environment-dependent.

2. `openThread`/`jumpToEnd` now target `historyEl` (good — formerly
   `document.querySelector('.el-main')`, which was a leak of the shell's layout
   into the pane). Keep that: a pane that scrolls the shell is a pane that
   re-motors the app. The current `historyEl.scrollTop = 0` on thread switch is
   fine. One nit: `quote()` still does `document.getElementById('aim-composer')`
   to focus — a pane reaching across to the composer by DOM id. If that composer
   ever moves to a component/scoped slot, the id is the coupling. Prefer a ref or
   a focus event. Low priority.

== Q5  what regression tests should pin this ==

Beyond the chat.spec you wrote, the high-value pins for the whole app:

1. **Route-factories agree with `views/*.js`**: every view registers; `ctx.views`
   has no dependency on another view's module. Cheap: assert the set of pane
   keys equals the set of route names the shell emits.
2. **API shape doesn't drift from the wire** (`api.js` vs the serve handler):
   `/api/state`, `/api/digest`, `/api/agents` all exist and return JSON with the
   keys the store reads (`statuses`, `terminal`, `phase`, `tasks`, `milestones`,
   `conversation`, `write`, `digest`). A regression test that loads `/api/state`
   as each of the three registered identities and asserts the store's getters
   don't throw would pin the contract.
3. **Theme/status vocabulary**: all `board.statuses` have a `STATUS_COLOR` and
   `STATUS_TYPE`; else Kanban/Items render a default tag and a reader can't tell
   a new status from a missing mapping. Cheap and high-signal.
4. **The gate-vs-pane invariant**: no pane filters tasks it was sent. Hard to
   test directly, but a proxy is: the payload already applied visibility, so a
   pane never imports `task_visible`-like logic. Grep-level / taste, not a spec.
5. **No pane reaches the shell or the composer by doorway-selector** — the
   `document.querySelector('.el-main')` / `getElementById('aim-composer')`
   couplings. Pin by convention (they're few); a weak regex lint is fine.

== The one structural suggestion worth doing ==

The flatten-channels/rooms/mail into one "recent rows" feed now exists in TWO
places that will drift: your uncommitted OverviewPane `recent` computed, and
ChatPane's `threads` computed (which groups them as threads, but for a *mail

both Overview and Chat from it, and let Chat keep its grouping view on top. That
is the single highest-leverage dedup in the app and it removes the duplication
your own edit just created on the second surface.
