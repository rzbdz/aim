== 1. What it does, and the one thing it deliberately does not do ==

Four verbs under `task`:

    aim task doorbell create --as a --channel c --id T-0001 \
        --url https://hooks.example.invalid/a2a --token <secret>
    aim task doorbell list   --as a --channel c --id T-0001 [--json] [--show-token]
    aim task doorbell rotate --as a --channel c --config-id cfg-… --token <new>
    aim task doorbell delete --as a --channel c --config-id cfg-… [--reason …]

`bin/aim-doorbell-hook` is not rewritten, not moved and not deleted. The accept
line says "the local hook stays the default and the config is additive", and I
took that as the substantive clause rather than a formality: the hook's own header
says `aim` must not know how any harness wakes a session, so moving it into `aim`
would be the daemon-dependent queue design/08 already rejected, arrived at
sideways.

So "additive" is *measured* rather than asserted. The suite runs the hook, captures
its bytes, creates a config, runs it again, and diffs. A config that changed the
hook's output would have made the local doorbell conditional on a webhook
somewhere else.

== 2. Configs are an append-only log, and that is a decision about secrets ==

`channels/<ch>/push.jsonl`, folded for reads. Rotation and deletion are appends: a
`doorbell_rotated` record supersedes the token it replaced rather than erasing it,
so "which secret was live when this was delivered" stays answerable. A manifest is
a read-modify-write and that is the lost update this repo already measured once.

`aim verify` now covers `push.jsonl` with the channel's other chains. An unverified
chain is a decoration — the file carries `prev` and `hash` that nothing reads,
which looks like tamper-evidence and is not. It holds a secret and I think that is
an argument *for* checking it rather than against, since the history is what makes
the rotation question answerable and a history nobody verifies is one anyone may
rewrite. Only TAMPER lines are printed, never contents, so verifying prints no
secret. The suite breaks the chain deliberately and asserts `verify` notices.

Masking, which I want you to look at because it is a judgement call:

  * The token is masked on every read shape (`list`, `--json`), returned on
    `create` (the caller just sent it), and returned in the clear by exactly one
    verb — `rotate` — which says so in its name and in its output.
  * The mask is a **comparison**, not a fixed `***`: `<masked:NB:sha256:…>`. §13.2
    asks for rotation, and rotation is a comparison — a caller who cannot tell a
    rotated token from an unchanged one will rotate on a schedule instead of on
    evidence. It leaks nothing a holder of the token does not have.
  * What it is *not* is a permission model. This store is read by root and by
    every `aim` verb, and I have said so in the code rather than implying the mask
    protects anything at rest. If you want the token out of `push.jsonl`
    altogether, that is a different design and I would rather hear it now.

== 3. Four refusals, each citing the spec rather than a preference ==

  * no token — the accept line's rule. §4.3.3: the agent presents the credentials
    on every notification, so a config without one names a webhook any process on
    the host can ring.
  * `token` vs `authenticationInfo.credentials` disagree — §4.3.3 sends the
    *credentials* as the header value, so two secrets means one is never presented
    and a reader who checked the other would see it as valid.
  * not http(s) — §4.3.3 delivers the notification as an HTTP POST, so `file:` and
    bare paths name a config that can never fire.
  * remote plain `http://` — §13.2 says webhook URLs SHOULD use HTTPS. It is a
    SHOULD, so `http://localhost` is accepted and a *remote* one is not. If you
    think a SHOULD should not be a refusal, that is a one-line change and I would
    rather you said so than left it.

One rule, two spellings: `aimboard.a2a.validate_push_config` holds the rules and
`bin/aim` imports it late, so a JSON-RPC client gets `-32602 fieldViolations` and
the CLI gets a sentence, from one implementation. The suite asserts both refuse
the same *field* for the same input. And `create_push_config` gates before it
validates, for §13.1's reason applied to the write path: answering "bad url" for a
task the caller cannot see has told them the task is there.
