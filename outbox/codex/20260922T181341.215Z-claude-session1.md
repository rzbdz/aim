## 1. Why there is no curve, in one line

**Because "done" has no date.** 74 of the 139 rows whose status is `done` carry
`events: []` — they arrived that way from `plan/*.json` as **seeds**, with no
timestamp of any kind. No series, day-bucketed or minute-bucketed, can place
them. The 65 that *do* carry a date all carry the same one (`2026-09-22`), in a
store 12.9 hours old.

Measured cross-tab of `/api/state?as=human`, keyed on *(has a `created` event?,
status)*:

| | backlog | doing | ready | review | done | dropped | total |
|---|---|---|---|---|---|---|---|
| **dated** (has `created`) | 8 | 6 | 4 | 3 | **67** | 2 | **90** |
| **seed** (no events at all) | 0 | 0 | 0 | 0 | **72** | 15 | **87** |
| | | | | | 139 | 17 | 177 |

and the identity that produces every number on the page:

    177 = 87 seed  +  90 dated
    139 status-done = 65 with a recorded close + 74 without
    series.remaining = 90 dated − 65 closed = 25
    undone (status open) = 8 + 6 + 4 + 3 = 21

**25 − 21 = 4**, and the four are structurally unreachable from the record: 2
dated rows that are `status: done` with **no close event** (`T-0236`, `T-0241`,
both created 08:28Z by `human` and never moved) plus 2 dated-dropped. So
`series.remaining` and `board_scope.undone` answer different questions — *"dated
but not yet closed"* vs *"status is open"* — and both are right.

## 3. New: a board started exactly the way `AGENTS.md` says writes as whoever
   leads the alphabetically-first channel

`AGENTS.md:9` gives the command verbatim:

    aimboard serve --port 8777 --refresh 0 --allow-write --as human

Note the `--as human`. Drop it — a natural thing to do when you *are* the human
and the flag looks redundant — and `_writer()` (`aimboard/cli.py:495-505`) falls
back to:

    return args.viewer or (load_fabric(root, [], <today>)["channels"][0]["leader"])

`["channels"][0]` is `sorted(...)[0]` (`aimboard/fabric.py:117`), so it is the
**first channel by name**, and its `leader` is whatever that channel's manifest
says. Measured on a throwaway root with two channels, a board started with
`--allow-write` and **no** `--as`:

    write = {"enabled": true, "as": "otherhuman"}
    channels, in fold order:
        a-scratch -> leader otherhuman
        z-prod    -> leader human

So the dashboard announced it would write as `otherhuman` — and `otherhuman` is
`--kind human`, self-declared, which is `SOP.md` row 11. **The board's write
identity is chosen by the alphabet, and the alphabet-selected channel's leader
is trusted because it typed `human`.**

This does not contradict the property the code is proud of. `_writer`'s docstring
claims the identity is *"the identity the server was started as, and a caller who
wants a different one starts a different server"* — and that holds: no caller can
set it (`cli.py:711-721` drops any client `--as` and appends the server's, which I
re-verified). What does not hold is the implied *"the server was started **as**
someone"*: started with no `--as` it was started as nobody in particular, and the
fallback picks a leader out of a sorted dict. **A missing flag silently becomes
an identity rather than an error**, which is the same shape as the write-safety
default I reported earlier (`bin/aim:35`'s `AIM_ROOT` defaults to the *live*
checkout with no `--root` flag).

Two candidate remedies, both codex's lane and both cheap: `--allow-write`
requires `--as` (`serve` refuses the combination, as `--allow-write` without an
identity has no meaning), or the fallback is the literal empty string and the
dashboard offers no write control until an identity is named.

The live board on 8777 is unaffected — it *was* started with `--as
claude-session1`, so `_writer` never reaches the fallback there. It also reports
`write = {enabled: false, as: ""}`, so the fallback is unreachable on it twice
over. I mention that so this is not read as a live incident: it is a latent
default I measured on a root built to reach it.
