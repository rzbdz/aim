== 1. The shape ==

One dispatch point, `aimboard.a2a.handle_rpc(method, params, ...) -> (response,
mime)`, and one thin HTTP branch in `cli.py` (`_rpc_POST`): parse, load the
state, call, serialise. The same split as /api/state - cli routes, a2a
translates - and for the same reason: a second implementation of "what GetTask
does" is the second-answer-to-one-question failure this repo keeps finding.

Seven operations route to the real functions you already reviewed: GetTask,
ListTasks, GetExtendedAgentCard, and the four push ops (with push.jsonl folded
into the flat (task, config) list the module's push functions take). D17 is
untouched because those functions already implement it - I changed nothing
under them, and the new checks prove the wire agrees:

  * GetTask for a task the caller cannot see -> -32001, no count
  * GetExtendedAgentCard -> the viewer's own card (positive control)

Four have no backing - SendMessage, SendStreamingMessage, CancelTask,
SubscribeToTask - and answer `-32004 UnsupportedOperationError`. That was the
plan I proposed twice before the redirect, and it is what I built: a surface
that claims the operations it cannot perform is the pushNotifications-flag lie
one level down.

== 2. Three calls I made, and where each lives ==

  * **Viewer = the server's `--as` identity, never a request field.** Same rule
    as /api/command and mcp.py. design/07 §7's "auth before outside localhost"
    is not weakened: the server is still 127.0.0.1-bound, and the identity
    cannot be forged from the wire.
  * **Streaming answers over `text/event-stream`**, with the honest error as
    the one SSE event. A streaming method that answers application/json is a
    method that lied about being streamable; an SSE client would hang forever
    on a JSON body it never asked for.
  * **`--allow-write` does not gate /rpc.** This is the one judgement I want
    your eye on. A2A callers are the fabric's peers, not the dashboard's
    browser, and §3.4 makes pushNotifications only meaningful if
    CreateTaskPushNotificationConfig can actually be called - the doorbell
    verbs stay callable, which is the capability the card claims. If you read
    it differently this is a one-line change at the route; the reasoning is in
    the comment at cli.py's `_rpc_POST`.
  * (smaller) an unknown method answers JSON-RPC's own `-32601`, not one of
    the nine A2A types - it never was an A2A operation.

Note that /rpc CreatePushNotificationConfig is currently *in-memory*: it
returns the config the module would persist, folded into the same shape as the
CLI's records, but it does not append to push.jsonl - the CLI's `task doorbell
create` remains the writer, which preserves "one rule, one owner" for the
write discipline. If you want /rpc to be a real writer, that is a decision
about the write path and I would rather make it deliberately than by
accident. Say the word and I will wire it through the same `append_chained`
under the channel lock.
